# Plumb's scripts: every command and flag

Skills link here instead of repeating the list. `<script> --help` is the final word on flags.

**Who runs what.** The project's design-system skill holds its own copies of the engine
(`<skill>/scripts/build-tokens.py`, `audit.py`, `build-prototype.py`, `_plumb.py`): those are what `make`, CI and the
skills run, so everyone applies the same rules. The hooks never run them: they run the plugin's own installed copies
on the project's files (the trust boundary in `SECURITY.md`). `<skill>` is the `Design system:` path in `PLUMB.md`. The
plugin's helpers (`detect.py`, `scaffold.py`, `version.py`, `screenshot.py`, `check-tour.py`) run from `<ROOT>/scripts/`, where `ROOT` is
the plugin root (`${CLAUDE_PLUGIN_ROOT}`, or the skill's base directory + `/../..`).

**Python.** Every command starts with the project's Python command from `PLUMB.md` (`Python: \`python3\``; `py -3` or
`python` on Windows). Below it is written `python3`. Run from the project root. Commands never need a shell feature
(no pipes, no `cd … &&`).

**Where output goes.** Nothing is written outside the project. Every default output path is inside it (the audit
report and the pages in the docs folder, the generated files in the skill and the copies); a file you need only for
one step (an answers file, a `--snapshot`, saved `--json` or `--check` output to read back) goes in
`<root>/.plumb-tmp/` (with a `.gitignore` of `*`; "Temporary files" in [placement.md](placement.md)), never `/tmp`,
`%TEMP%` or a folder above the project.

**Errors.** Every script prints `error: <what>` then `fix: <exact command>` (or `ask the user: …`) and never a
traceback. Bad input exits 2. Do what the `fix:` line says, or ask the user when it says so; never guess.

**Never by hand.** Generated files (`[G]`: `tokens.css`, `tailwind.tokens.js`, the Swift and Kotlin
themes, `specimen.html`, `prototype.html`, `app.html`, `screens.html`, `prototype/screens.json`, `tours/*.html`, the proposal pages,
`audit-*.html`, and Plumb's block in each web copy) are
written only by these scripts; Plumb's own files (`[P]`: `<skill>/scripts/*`, `<skill>/templates/*`,
`assets/platforms/README.md`) only by `scaffold.py` during `/plumb:upgrade`. The edit check refuses hand edits to both.

**Web copies are the project's file with Plumb's block in it.** A copy listed in `$extensions.plumb.web.copies` (e.g.
`app/globals.css`) holds the generated CSS between `/* plumb:start — GENERATED by Plumb, do not edit inside */` and
`/* plumb:end */`; every line outside the block is the project's and is edited by hand as usual. The build updates
only the block and keeps the rest byte for byte; `--check` and the audit's drift rule compare only the block; the
audit checks the rest of the file like any stylesheet (and reports `block-override` when the rest redefines
`@custom-variant dark` or sets the tokens' variables in an `@theme` block); the edit check refuses only an edit that
changes the block (a shell write or a removal of the copy is still refused, as the hook cannot see what it changes: its
message says only the block is Plumb's and to use the edit tool for the rest).

**The docs folder.** The scripts read it from the tokens file's `$extensions.plumb.docs_dir` (default `docs/design`):
the specimen, the prototype pages, `screens.json`, tours, proposals and reports all go there. `PLUMB.md`'s
`## Prototype` lines name the same files for people and agents. When `PLUMB.md`'s `Main:` path sits in another folder,
the two disagree: a skill says so, asks the user which is right, and then fixes the other one (the tokens file's
`docs_dir` through `/plumb:update`, or the `## Prototype` lines of `PLUMB.md`), each change shown and asked first.
Never guess which one wins.

## build-tokens.py: the tokens → every theme

`python3 <skill>/scripts/build-tokens.py [--check | --contrast | --migrate | --css-vars | --overrides [--apply]] [--root SKILL_DIR] [--project PATH]`

| Flag | Does |
|---|---|
| (none) | Writes every output from the one tokens file: web CSS (`tailwind-v4`, `tailwind-v3` + `tailwind.tokens.js`, or `css`), Plumb's block in each copy in `$extensions.plumb.web.copies`, the iOS and Android themes for the platforms listed, the contrast block in `references/dark-mode.md`, `<docs>/specimen.html`, and the token region of `prototype.html`, `app.html`, `screens.html`, `tours/*.html` and the generated proposal pages (each variant's `app.html` too) when they exist. Deterministic: running it twice changes nothing. |
| (the specimen) | A `<docs>/specimen.html` that this script did not write (no `GENERATED by …/scripts/build-tokens.py from <id>.tokens.json` header: another tool's page, or one written by hand) is never replaced: the build stops before writing anything, exit 2, `error: <docs>/specimen.html is not Plumb's …`, `fix: ask the user before moving it out of the way (mv … specimen.before-plumb.html; -2, -3 … when taken), then run …`; `--check` prints `not Plumb's: …` and a `fix:` line, exit 1. An empty page (a build cut short) is rewritten. |
| (a web copy) | A new copy is the block alone. An existing file with no block gets it near the top, after the statements that must stay first (`@charset`, `@import`, `@use`/`@forward`, `@tailwind`, `@layer a, b;`, `@config`/`@plugin`/`@source`; read token by token, so a `;` inside a string, a `url(...)` or a comment, as in a Google Fonts `@import url("…wght@400;700")`, does not end a statement), and keeps every other byte (its line endings too, and a missing final newline): taking the block out gives the file back exactly. The build prints `note: added Plumb's block to <copy> …` that first time; before it, `--check` prints the exact change as a diff: show it to the person and ask. When the rest of the file already imports Tailwind (`@import "tailwindcss"`), the block leaves its own import out. A whole copy an older build generated (its `GENERATED by …build-tokens.py` header, no block) becomes the block, with a note. Broken markers (not exactly one of each, start first) exit 2 and write nothing. |
| (dark and motion) | The template's `{{@dark}}` follows `$extensions.plumb.web.theme_switch`: `both` (default) = dark values under `@media (prefers-color-scheme: dark)` for `:root:not(.light)` **and** under `.dark`; `system` = only the media rule; `class` = only `.dark`; `data-theme` = only `[data-theme="dark"]` (and `[data-theme="light"]` instead of `.light`), the attribute next-themes sets by default. A `.light` rule always puts the light values back. `{{@dark-variant}}` (Tailwind v4) writes the matching `@custom-variant dark`; `tailwind.tokens.js` (v3) names the matching `darkMode` in its header. `{{@reduced-motion}}` follows `$extensions.plumb.motion.reduced`: `none` (default) stops every animation and transition, `keep-fades` keeps opacity and colour transitions and stops all movement. `keep-fades` never adds a transition: elements whose transition is only a fade (`.transition-opacity`, `.transition-colors`, or `.motion-fade` in a plain-CSS project) keep theirs, and their `::before` / `::after` keep only opacity and colour transitions; every other transition (pseudo-elements included) and every animation stops. A setting given while the project's template predates these lines prints a `note:` (refresh the template with `/plumb:upgrade`); a template with the lines and no setting builds the default and prints a `note:` asking to record the choice, or to keep the default with `build-tokens.py --migrate` (create and scaffold always write both settings). The project's own `@custom-variant dark` or variables in the tokens' namespaces in an `@theme` block outside the block print a `note:` (they add to or override the design system; `--overrides` maps them onto tokens). |
| `--check` | Writes nothing; exit 1 naming every stale or missing output, copy (its block only) or prototype token block. For a stylesheet that would get Plumb's block for the first time it also prints `would add Plumb's block to <copy> …` and the exact change as a unified diff (`--- a/<copy>` / `+++ b/<copy>`), so the person can see and agree to it before the build writes. |
| `--contrast` | Rewrites only the contrast evidence block of `references/dark-mode.md` (exit 2 if the file or its markers are missing). Exits 0 even when pairs fail: the audit is the gate. A failing pair's proposed value passes with 0.5 to spare, so the audit's `contrast-headroom` suggestion (under 0.3) never flags a value Plumb proposed. Values are stepped in OKLCH lightness with hue and lightness kept (chroma is reduced when the colour leaves sRGB, channels are never clipped, so the hue stays within about a degree). For `on-X` on `X` where `on-X` is white or black (text on a filled control), the block (and the audit's `contrast` fix) lists two options per failing theme with their ratios: step `X` (same hue, `on-X` stays as it is) and step `on-X`. "White or black" means near-neutral and near an end: OKLCH chroma at most `NEUTRAL_CHROMA` (0.02) and WCAG relative luminance at least `NEAR_WHITE_LUMINANCE` (0.85) or at most `NEAR_BLACK_LUMINANCE` (0.03), so `#fafafa` and `oklch(0.985 0 0)` count and a light grey (`#d0d0d0`) or a tinted near-white does not (those keep the single "nearest passing" value). For a filled control (`primary`, `danger`, `success`, `accent` …) the `X` option is first; when `X` is a surface-family role (`background`, `page`, `surface*`, `sunk`, `raised`, `card`, `popover`, `sidebar`, `*-container`, or named in `contrast.surfaces`) the `on-X` option is first, because stepping a whole surface is a big change. When the token to change is an alias (`{color.brand}`), the line says so and names the source token to change. Stepping `X` changes every use of `X`: show it before asking. |
| `--migrate` | Brings the tokens JSON up to the current schema by **adding** missing settings; never removes or changes a value. Used by `/plumb:upgrade`. It also writes the defaults the build applies when a setting is missing (`web.theme_switch: "both"`, `motion.reduced: "none"`), so the build's "not set" note ends with this one command; change them later with `/plumb:update`. |
| `--overrides` | Read only. Prints, as JSON, what each existing web copy sets outside Plumb's block that the audit reports as `block-override` (a stock create-next-app or shadcn `globals.css`: `@theme inline { --color-background: var(--background); --font-sans: var(--font-geist-sans); … }`). Per copy: `overrides` (each `line`, `name`, `value`, `kind`: `token` = it replaces that token (when the app's value differs from the token's, its light or dark colour or a length such as a radius worked out in px, `notes` says the look changes, with both values), `new-name` = it adds a name to the tokens' namespace, `namespace` = `--color-*`, `dark-variant`; the `token` it is or becomes; the project's `project_values` light and dark; the `token_change`: `add` a token (an alias of the matching role, e.g. `color.foreground` = `{color.on-surface}`; shadcn's `card`/`sidebar` → surface, `popover` → `surface-raised` (or `raised`) when the tokens have one, else surface, `secondary`/`muted`/`accent` → sunk, their `-foreground` → on-sunk or on-surface (`muted-foreground` → on-surface-muted), `border` → outline, `input` → outline-input, `ring` → primary, `destructive` → danger; a `sidebar-<x>` / `sidebar-<x>-foreground` goes first to the tokens' own `color.sidebar-<role>` / `color.on-sidebar-<role>` when it exists (`<role>` is `<x>` or its synonym: `accent` ↔ `active`; its colours differing from the app's is a `notes` look change), else a `sidebar-<x>` with the same colours as `<x>` goes where `<x>` goes. The colours decide too: when the role token's light and dark colours differ from the app's, a token of the same kind (text or surface) that has the app's exact colours wins (extract recorded them); otherwise the role stays and `notes` says the look changes (`… the look changes; ask the user …`): show it and ask; otherwise the project's own light and dark values, `oklch()` read as sRGB and a translucent one kept as `#rrggbbaa`, and a colour the app sets only in `:root` marked `"same-in-dark": true` (what the app does today; listed in `notes`); a radius step from `calc(var(--radius) ± Npx)` when `--radius` has a value in the file) or `prepend` the font variable the app loads, e.g. `var(--font-geist-sans)`, to the font token when that token names that font or only a system stack), `remove_lines` (the overriding lines, the project variables that only fed them, and the blocks that become empty; never a line of Plumb's block), `replace` (uses of those variables → the token's variable; a literal `font-family` → `var(--font-sans)`), `project_variables` (each with `used_in`: the other UI files, `file:line`, that still read it; Plumb's own pages in the docs folder and the skill are never listed) and `by_hand` (what only the person can decide, e.g. the app loads one font and the tokens name another; and, when PLUMB.md records `Routes: <path> (next-app)`, a next/font `.variable` the root layout applies on `<body>` and not `<html>` while an override puts that font's `var(--font-…)` into the tokens: "move `<name>.variable` to the `<html>` className in <file>:<line>", because on `:root` the variable is undefined and the whole font stack is invalid; no `Routes:` or another kind: no check. The font may be defined in the layout (any options, a `src` array included) or in a local file the layout imports it from (one relative hop); a font from anywhere else is named in the item as one Plumb could not check. `<body>` / `<html>` inside comments are ignored). Show it to the person and ask before `--apply`. Use it when the audit reports `block-override` or the build prints its override note. |
| `--overrides --apply` | Makes exactly that plan: the token changes in the tokens file, then the removals and replacements in each copy (line endings kept). Checks every copy first: if Plumb's block would change, it writes nothing and exits 2. Leaves `by_hand` items alone and lists them, and prints a `note:` naming the files that still read a removed variable. What the audit reports afterwards is the app's own code (`/plumb:audit fix`). **Only after the person's OK** to the plan. Then rebuild and audit. `--apply` without `--overrides` exits 2. |
| `--css-vars` | Prints the tokens as plain CSS custom properties (`:root`, the md breakpoint, `.dark` and `prefers-color-scheme`): the block prototypes and proposals inline. Plumb's own pages (specimen, prototype, screens, report, tours, proposals) give an app font variable a fallback there (`var(--font-geist-sans, Geist, system-ui, sans-serif)`), so outside the app they never fall back to serif; the app's own CSS keeps the tokens as written. |
| `--root SKILL_DIR` | The design-system skill folder (default: the skill this script sits in). |
| `--project PATH` | The project root when no `PLUMB.md` is found above the skill. |

Exit codes: 0 ok · 1 stale (`--check`) · 2 bad input (`error: <token>: …`).

## audit.py: the design audit

`python3 <skill>/scripts/audit.py [PATHS...] [--json] [--html [OUT.html]] [--add-review REVIEW.json] [--no-tokens] [--root SKILL_DIR] [--project PATH]`
`python3 <skill>/scripts/audit.py --quick FILE [--before -|PATH]`

| Flag | Does |
|---|---|
| `PATHS...` | Files or folders to check (default: the whole project, narrowed by `PLUMB.md`'s `UI files:`). Put flags after them. |
| (full mode) | Every per-file rule, then the cross-file rules (contrast, drift, prototype fidelity, suggestions). Prints `file:line: <severity> <rule>: <message>` + `  fix:` per finding and a summary. Rules: [rules.md](rules.md). |
| `--json` | The findings as JSON: `{"version","mode","checked","errors","warnings","suggestions","findings":[{"rule","severity","file","line","message","fix"}]}` (+ `scales` in inconsistency-only mode, + `agent_review` with `--add-review`). |
| `--html [OUT.html]` | Also writes the report page (default `<docs>/audit-YYYY-MM-DD.html`): summary, Issues, Improvements ranked by impact, filters, light and dark. Terminal output and exit code are unchanged. Write `--html=OUT.html` or put it after the PATHS. |
| `--add-review REVIEW.json` | With `--html`: merges the agent's review (a JSON list of `{severity, file, line?, message, fix, why?}`) into the report as a separate **Agent review** section, each finding marked so. Never changes the terminal findings, the counts or the exit code. Bad file → exit 2 naming the entry and key, no report written. See [rules.md](rules.md#agent-review-not-a-rule). |
| `--no-tokens` | Inconsistency-only mode even when a tokens file exists (infers the scales from the code). Automatic when there are no tokens yet. |
| `--quick FILE` | One file, only the errors an edit adds, JSON out (what the edit check runs). `--before -` reads the old text on stdin; `--before PATH` from a file; without it the file counts as new. Never runs the cross-file rules. |
| `--inventory` | Added for `/plumb:extract`: every value in use with counts and `file:line`, and the proposed clusters (see the extract skill). `rounded-*` classes count at the project's own `@theme` / `@theme inline` `--radius-*` values (plain lengths, `var(--radius)`, `calc(var(--radius) ± N px or rem)`), Tailwind's defaults only for sizes it does not define. Colour clusters stay within one source (`variable` = a named CSS variable, `palette` = a Tailwind palette class, `literal`: any other value, including theme objects and Swift/Kotlin names); each cluster says which, and the same hex in two sources stays two groups. The base `--radius` counts only on `:root` / `html` / `body` / `*` or in `@theme` (a `.dark` or `[data-theme]` override is ignored); when several CSS files define a name, the file with an `@theme` block wins, then path order, and the output names the files used. |
| `--root`, `--project` | As for build-tokens.py. |

Exit codes: 0 no errors (warnings and suggestions allowed) · 1 errors found · 2 nothing checked or bad input.

## build-prototype.py: the main prototype and its map

`python3 <skill>/scripts/build-prototype.py [--check] [--map ID --route=ROUTE --files GLOB ...] [--approve ID] [--synced ID] [--root SKILL_DIR] [--project PATH]`
`python3 <skill>/scripts/build-prototype.py --proposal NAME [--check]`
`python3 <skill>/scripts/build-prototype.py --check-tour FILE`

| Flag | Does |
|---|---|
| (none) | Assembles `<docs>/prototype.html` (the clickable app, the walkthrough player, decisions; use it to review), `<docs>/app.html` (every screen full window with no panels, `#/ID` and `#/ID/STATE` routes, the same screen scripts; use it to demo), `<docs>/screens.html` (every screen × state, light and dark side by side, control states; each screen's markup is in it once, shared by all its copies, so it grows with the screens, not screens × states) and `<docs>/prototype/screens.json` from `<docs>/prototype/screens/*.html`, `<docs>/decisions.md` and `<docs>/prototype/tours/*.json`; writes `<docs>/tours/<tour>.html` per tour, in the tour's `"view"`: the app view with the player on top (default) or the prototype page. No timestamps: rebuilding gives the same bytes. Any page it builds (these, the tour pages, the proposal pages) over 10 MB gets one `warning: <page> is <N> MB, …: over the 10 MB …` line naming every such page (also on `--check`; the exit code does not change), a `note:` naming the heaviest screen files (with their share of inline `data:` URIs) and a `fix:`: make the screen files smaller (inline `data:` images and large SVG into image files, long sample content cut), or git-ignore the pages and run the build in CI instead of `--check` (a git-ignored page is missing on a fresh clone), or keep them committed. Use it when: a page is slow to open or heavy in the repository; put the options to the user and ask which they prefer ([prototypes.md](prototypes.md)). **A page it did not write is never replaced:** a file at one of these paths (or a tour or proposal page's) without a `GENERATED by …build-prototype.py` header (another tool's page, or one written by hand) stops the build before anything is written: exit 2, `error: <page> is not Plumb's …`, `fix: ask the user before moving it out of the way (mv <page> <name>.before-plumb.html next to it, a tour page's one folder up; -2, -3 … when that name is taken), then run <the same command> again`, every such page named at once; `--check` prints `not Plumb's: <page> …` and a `fix:` line and exits 1. build-tokens.py leaves such a page alone too. An empty page (a build cut short) is Plumb's and rewritten. |
| `--check` | Writes nothing; exit 1 naming each stale or missing page, `app.html` included (or a stale token block); an edited shared file makes the pages stale too. A tour step naming a screen, state or element that does not exist exits 2. |
| (shared files) | `<docs>/prototype/screens/_shared/*.css` and `*.js` (and each variant's `screens/_shared/`): CSS inlined once per page, JS run for every screen before its own script, in name order. Part of every screen's approval hash (no shared files: the screen file's own hash, as before); an edit makes those approvals stale and the build's `note:` names the file. `</script`, `</style`, a network load (`fetch(`, `new XMLHttpRequest`, `import`, CSS `@import`, `url(https://…)`) exit 2 naming the file and line; a CSS selector not starting with `[data-screen]` is a `warning:` (on `--check` too). The `_shared/` folder is reserved: nothing in it is a screen. Use it when: several screens share an app shell's layout or a helper ([prototypes.md](prototypes.md), "Shared files"). |
| (change ids) | `data-guide="F01 · …"` (a letter and digits, then `·`): with `<docs>/prototype/changes.md` present, every id the main screens use must be listed there (`- **F01** title: what and why`), else exit 2 naming the screen file and the id; a listed id no screen uses is a `warning:`. No `changes.md`: not checked. |
| `--map ID --route=ROUTE --files GLOB ...` | Records a screen's route (`--route=/billing`, `--route=/b/:id`) and source files (globs from the project root) and their hash, the baseline the audit compares against. `status` becomes `built` once every glob matches a file. Confirm route and files with the user first. Write the route joined to the flag with `=`: a bare `/` as its own argument after the flag looks like a path to Copilot CLI, which then asks for access to the whole file system; `--route=/` does not. |
| `--approve ID` | Records the user's approval: git `user.name` (else `$USER`/`%USERNAME%`), today's date, the hash of the screen file plus the shared files that reach it (`_shared/`, when there are any); clears "synced from code". **Never run `--approve` without the user's explicit yes to that screen, given in this conversation** (not for a synced screen, not because a build passed, not for several screens on one general OK). Editing the screen or a shared file afterwards makes the approval stale. |
| `--synced ID` | Marks a screen updated to match code that was already built (a small fix, code written before Plumb); listed for the user to confirm, never blocking. |
| `--proposal NAME` | Builds `/plumb:prototype`'s variants instead of the main prototype: for each `<docs>/prototype/proposals/NAME/<variant>/screens/*.html` (+ optional `idea.md`), that variant's `prototype.html`, `app.html` and `screens.html` (light and dark, the token block inlined), and `NAME/index.html` with the variants side by side ("Review: prototype.html · Demo: app.html" per variant). Generated and byte-stable; `screens.json` is not touched. With `--check`, exit 1 when one is stale or missing. Change ids: every `data-guide="F01 · …"` id a variant's screens use must be listed in `NAME/changes.md` (exit 2 naming the screen file and the id, also when there is no `changes.md`; on `--check` too); a listed id no screen uses is a `warning:`; the index lists the changes and where each is used. Use it when: a proposal changes an existing screen and the reviewer should see what changed ([prototypes.md](prototypes.md), "Change ids"). Does not combine with `--map`, `--approve` or `--synced`. The main build (and build-tokens.py) refreshes the token block of every generated proposal page. |
| `--check-tour FILE` | Checks one tour file (`<docs>/prototype/tours/<id>.json`, or just `<id>`) against the screens exactly as the build does and writes nothing: `ok: <file>: <n> steps (<mode> mode, <view> view) match the screens`, exit 0; a bad field, unknown screen or state, or a selector that matches nothing exits 2 with the line and the fix. It also **warns** (stderr, exit code unchanged) when a step's target, label or action element sits in an element the screen's own CSS hides at some frame widths: `display: none`, `visibility: hidden` or an off-canvas transform (`translateX(-100%)` and the like) in a top-level rule that an `@container plumb-frame (min-width: …)` rule undoes (or the reverse): `warning: <file>:<line>: step 3, steps[2].target ".side-nav a" sits inside nav.side-nav, which the screen's CSS hides (display: none): visible only when the frame is ≥ 48rem`. It reads only the `_shared/*.css` files and the screen's own styles, in the page's order: their top-level rules and `@container plumb-frame` blocks (`min-width`/`max-width`/`width`, also `inline-size`) (cascade by `!important`, specificity, order); a selector or query it cannot read is left out. Use it when: a tour was written or changed, before the browser pass (`check-tour.py`). A warning matters when the tour plays where the frame is narrower than that (the prototype page's frame is narrower than the window). Does not combine with other flags. |
| `--root`, `--project` | As for build-tokens.py. |

`screens.json` is written only by this script (never by hand). Every command rebuilds the pages. **A broken tour does not
block the map:** `--map`, `--approve` and `--synced` still write `screens.json`, print a warning naming the tour problem,
leave the pages as they were and exit 0; the next build or `--check` exits 2 on the tour until it is fixed. The same
holds for a change-id problem (an id missing from `changes.md`, a duplicate) and a refused shared file.

Exit codes: 0 ok · 1 stale (`--check`) · 2 bad input (a screen file with no `data-screen`, a broken tour, …).

## scaffold.py (plugin): lay the skill into a project, move it, verify it

`python3 "<ROOT>/scripts/scaffold.py" --project-root P --name NAME --skill-dir D --platforms web,ios,android --styling tailwind-v4|tailwind-v3|css [--answers answers.json] [--docs-dir docs/design] (--dry-run | --confirm TOKEN)`

| Flag | Does |
|---|---|
| `--project-root P` | The project root (required in every mode). |
| `--name`, `--skill-dir`, `--platforms`, `--styling` | Required to lay the skill: product name (shown in the docs; any words), skill folder relative to the root (`.claude/skills/<project>-design-system`), platforms, web styling. |
| (project id) | The tokens file `<id>.tokens.json`, `$extensions.plumb.project` and the theme names use one id: the skill folder's name without `-design-system` (the placement detect.py proposed and the user confirmed), else detect.py's rule: the root `package.json` name (no `@scope/`), else the folder name, lower case with hyphens. `--name "Front Desk"` with package `frontdesk` gives `frontdesk` everywhere. |
| `--answers answers.json` | The interview answers (colours, type scale, spacing, radius, motion, icons, PLUMB.md values, `theme_switch` both/system/class/data-theme, `reduced_motion` none/keep-fades, `reset_palette` true/false, `routes`…); see the script's docstring. `routes` is `PLUMB.md`'s `Routes:` (the page folders or router files you found and the user confirmed, each `<path> (<kind>)`, kinds `next-app`, `next-pages`, `nuxt`, `sveltekit`, `angular`, `router`, e.g. `frontend/src/app (next-app)`; or `none`; table: [placement.md](placement.md)); an entry without a kind is refused; unanswered, a web project's `Routes:` reads as not recorded and the route checks stay off. `reset_palette` is `$extensions.plumb.web.reset_palette` (create on a new app: `true`; extract on an existing app: `false`); unanswered, `false` when the app's UI files already use Tailwind's default palette classes (a `note:` says so), else `true`. Without a `ui_files` answer, `PLUMB.md`'s `UI files:` comes from the project's stack (detect.py's scan: Angular gets its component files) or else the platform default ([placement.md](placement.md)). A `web_copies` path that already exists with the project's own CSS prints a `note:` that the tokens build adds Plumb's block to it and keeps the rest. |
| `--docs-dir` | Where the design pages live (default `docs/design`). |
| `--dry-run` | Prints `would write:` / `skip:` and writes nothing. Its last line is `confirm: … plus --confirm <token>`: the token fits exactly this command, answers file and file list. Use it when: always first; show the person the list. |
| `--confirm TOKEN` | The real run, after the person's OK on the dry-run list: the same command without `--dry-run`, plus `--confirm <token>` exactly as the dry run printed it. Without it nothing is written (`error:` + `ask the user:` show the dry-run list); a token from another list (the answers, arguments or files changed since) is refused the same way: run the dry run again and show the new list. |
| `--relocate FROM TO` | Moves the skill folder and updates every reference (PLUMB.md, the AGENTS.md/CLAUDE.md row, Makefile), then runs the moved `build-tokens.py --check` (regenerating once when only the header paths changed). |
| `--verify` | Checks that PLUMB.md's skill path exists and that the AGENTS/CLAUDE row, the Makefile and the copy targets point at it, and that every `make` target PLUMB.md names (`(make tokens)`, `(make tokens-check)`, `(make design-audit)`) exists in the Makefile: no Makefile, or a missing target, is a `problem:` whose `fix:` is the plugin's `templates/Makefile.snippet` (or taking the `(make …)` note out of PLUMB.md). It checks `Routes:` (each recorded folder or router file exists; an entry without one of the kinds `next-app`, `next-pages`, `nuxt`, `sveltekit`, `angular`, `router` is a `problem:`; not recorded is a `note:`) and `UI files:` (a value that matches 0 files while the project has UI code is a `problem:`; a folder glob that matches nothing is a `note:`) and `Allowed raw values:` (a pattern that matches 0 files is a `warning:` plus a `fix: ask the user:` line, never a problem; `none` and a matching pattern are quiet). When the user gave no `allowed_raw`, the default is each detected web package's primitives folder from the repo root: `components.json` `aliases.ui` resolved through the package's tsconfig/jsconfig `paths` (`@/` means `src/` without one), else its existing `components/ui` folder; `none` without a web platform; `components/ui/**` when no package is found. In a git repo it runs `git check-ignore` on the skill folder, `PLUMB.md` and the docs folder: an ignored one is a `problem: <path> is git-ignored by <pattern> … — the design system would never be committed` with a `fix: ask the user:` line that names the file the pattern is really in (`check-ignore -v`: a `.gitignore`, `.git/info/exclude` or the global excludes file) and the edit that works for its shape: `.claude/` becomes `.claude/*` plus `!.claude/skills/`; `.claude/**` gets `!.claude/skills/` and `!.claude/skills/**`; `.claude/*` gets `!.claude/skills/`; for the global file it also offers `!.claude/`, `.claude/*`, `!.claude/skills/` in the repo's own `.gitignore` (which wins over it); or another location. The dry run and the real run print the same lines as `warning:`. Prints `ok:` / `problem:` / `note:` and the `--relocate` command when the skill sits elsewhere. Exit 1 on any problem. |

**Ownership.** `[P]` files (`scripts/*.py`, `templates/*`, `assets/platforms/README.md`) are always overwritten
(`wrote:`); `[Y]` files are written only when absent (`skip: … (yours, kept)`). That is why `/plumb:upgrade` re-runs the
same command to refresh Plumb's files: the project's own files are never touched. Exit codes: 0 ok (`--verify`: 1 on
problems) · 2 bad input.

## detect.py (plugin): repo layout and stack

`python3 "<ROOT>/scripts/detect.py" --cwd PATH [--json]`: where the project and its UI live (git root, monorepo
packages, frameworks, styling, UI file counts, the `UI files:` value the stack needs (`ui_files`: Angular's component
files; `null` when the platform default fits), an existing `PLUMB.md`). Read-only; a first guess that `/plumb:init`
always shows the user to confirm. It also proposes `routes` (a guess at `PLUMB.md`'s `Routes:`), and for a UI
package in a subfolder repo-relative UI files (`frontend/src/**`); the block labels both as guesses. The proposed `project` id and skill folder (`<id>-design-system`) come from the same
rule scaffold.py uses (package.json name, else the folder name). Every field: [placement.md](placement.md).

## version.py (plugin): project vs plugin version

`python3 "<ROOT>/scripts/version.py" --project P --plugin "<ROOT>" [--json]`

| Flag | Does |
|---|---|
| `--project P` | The project root (or its `PLUMB.md`); the version is `PLUMB.md`'s first line `<!-- plumb vX.Y.Z · … -->`. |
| `--plugin R` | The plugin root (its `.claude-plugin/plugin.json` and `upgrades/`). |
| `--json` | `{"project": "1.0.0", "plugin": "1.2.0", "state": "same" \| "older" \| "newer", "between": ["1.1.0", "1.2.0"], "files_differ": []}`: `between` is every `upgrades/<v>.md` with project < v ≤ plugin, ascending, compared as numbers; empty unless `older`. `files_differ` (only when `same`): Plumb's own files in the design-system skill (`scripts/*.py`, `templates/*`, `assets/platforms/README.md`) that are missing or differ from the plugin's copies, line endings and a BOM ignored, as project-relative paths: another build of the same version, or a hand edit (the files cannot tell which is newer: `/plumb:upgrade` shows the evidence and asks). `PLUMB.md` is read as the hooks read it. Empty for a linked repo, a skill outside the project or not there yet. |

`older`, or `same` with `files_differ` → offer `/plumb:upgrade`. `newer` → a teammate upgraded with a newer plugin: print the commands for the user to
run in their own terminal (`claude plugin marketplace update plumb`, then `claude plugin update plumb@plumb`; in Copilot
CLI `copilot plugin marketplace update plumb`, then `copilot plugin update plumb@plumb`) and wait; never run them
yourself, and never downgrade the project.
Exit codes: 0 · 2 bad input (no `PLUMB.md`, no version line, a damaged `plugin.json`).

## screenshot.py (plugin): a headless screenshot with a browser already installed

`python3 "<ROOT>/scripts/screenshot.py" URL_OR_FILE --out PNG [--width W] [--height H] [--theme light|dark] [--wait MS] [--timeout S] [--browser PATH]`

| Flag | Does |
|---|---|
| `URL_OR_FILE` | An `http(s)://` or `file://` URL, or a local HTML file, optionally with a `#fragment`: `docs/design/prototype.html#screen-booking/empty` opens that screen in that state. |
| `--out PNG` | The PNG to write (folders created; an existing file is replaced only by a good shot). |
| `--width`, `--height` | Viewport in CSS px (default 1280 × 900; 390 × 844 for a phone). |
| `--theme` | `light` (default) or `dark`: the page's `prefers-color-scheme`. |
| `--wait MS` | Page time before the shot, so scripts can render (default 2000). |
| `--timeout S` | Stops a browser that hangs (default 60). |
| `--browser PATH` | Use this browser executable instead of searching. |

It finds Chrome, Edge or Chromium already on the machine: the PATH names `google-chrome`, `chromium`,
`chromium-browser`, `microsoft-edge` (and `-stable`, `chrome`, `msedge`); macOS app bundles in `/Applications` and
`~/Applications`; Windows `chrome.exe` / `msedge.exe` under Program Files and LocalAppData. It runs it headless with a
throwaway profile (inside a Plumb project in `<project>/.plumb-tmp/`, removed afterwards) and background networking off. **It never installs or downloads a browser.** Exit codes: 0 written ·
1 the browser ran but wrote no screenshot (or hung) · 2 bad input · 3 no browser:
`note: visual comparison skipped: no browser found` + `fix:`; skip the visual part, say so in the report, and run every
other check. A `#fragment` that scrolls to an anchor can come out blank in headless Chrome and Edge; the prototype's
`#screen-ID/STATE` routes work.

**Which browser, in order:** (1) the agent's own browser tool, if it has one and the organisation allows it; (2)
`screenshot.py` (a Chrome, Edge or Chromium already installed); (3) none: skip the visual part with the `note:` and its
`fix:` line in the report. Playwright is never installed for a project; it is used only in Plumb's own CI.

## check-tour.py (plugin): play a tour page headless and check every step

`python3 "<ROOT>/scripts/check-tour.py" <docs>/tours/<id>.html [--width 1280 --width 1440] [--browser PATH] [--timeout S]`

| Flag | Does |
|---|---|
| `PAGE` | A tour page `build-prototype.py` wrote (`<docs>/tours/<id>.html`, either view). |
| `--width W` | Window width in CSS px, repeatable (default 1280 and 1440; the window is W × 900). |
| `--browser PATH` | Use this browser executable instead of searching (screenshot.py's search). |
| `--timeout S` | Stops a browser that hangs, per width (default 120). |

It copies the page into `<project>/.plumb-tmp/` (its `<base>` pointed at the original's folder, so images resolve; a checker script added), runs the browser headless in the light theme with `--dump-dom` and `--virtual-time-budget` once per width, and reads the results the checker wrote into the page. The checker walks every step of the page's tour in guide mode, then in play mode, through the player's API (nothing waits real time) and checks per step: the page shows the step's screen and state; each target, label and action element (the match the player points at, `window.plumbPlayer.node(selector)`: its first match the player can show, so a match in another state does not count; with none, the reason is given for a match in the step's state) is laid out (not `display: none`), not `visibility: hidden` or `opacity: 0`, not zero-size, inside the window once the player scrolled to it, and not covered at its centre (by the walkthrough panel where the two really overlap, so a corner toast beside the centred panel passes; the panel is read where it is, at the bottom or at the top where the player moved it for a pinned element, and there the part below it counts; or by a screen's own fixed or sticky layer); the dock is not covered (`elementFromPoint` at its centre is the dock). The scratch copy and the profile are removed afterwards. **It never installs or downloads a browser.** Output: `ok: <n> steps × guide/play × 1280, 1440` (exit 0), or one line per problem, `step 12 (Users › Invite): the target ".invite" is hidden (visibility: hidden) at 1280 (guide, play)`, page script errors as `page: a script error: …`, and a `fix:` (exit 2). Exit codes: 0 · 1 the browser ran but gave no result (or hung; its `fix:` suggests a longer `--timeout` or another installed browser with `--browser`) · 2 problems or bad input · 3 no browser: `note: tour check skipped: no browser found` + `fix:`; say so and ask the user whether to continue (the static `--check-tour` still ran). Use it when: `/plumb:tour` built a tour page (step 3), or a screen a tour plays on changed. On Linux, a browser that stops with "No usable sandbox" (user namespaces off) is run once more with `--no-sandbox`, said in a `note:` line (a local offline page in a throwaway profile); never otherwise.
