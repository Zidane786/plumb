# Prototypes: screen files, variants, approvals

Every Plumb project has **one main prototype of the whole product**, always matching the real frontend:
`<docs>/prototype.html` (the clickable app), `<docs>/app.html` (the same screens full window, for a demo) and
`<docs>/screens.html` (every screen in every state, light and dark side by side). All are generated by
`build-prototype.py` from one source file per screen, so they cannot disagree. **prototype.html to review, app.html to
demo.** `<docs>` is the docs folder (default `docs/design`). Commands: [scripts.md](scripts.md#build-prototypepy-the-main-prototype-and-its-map).
`screens.html` stores each screen once and draws every state from it, so it grows with the screens, not their states.
Every page holds each screen file once. A page over 10 MB builds with a `warning:`, a `note:` naming the heaviest screen
files and a `fix:`: put both options to the user and ask which they prefer: smaller screen files (inline `data:` images
and large SVG moved into image files with a relative `src`, very long sample content cut), or git-ignoring the pages,
which makes `--check` fail on a fresh clone, so the project then runs the build in CI instead of `--check` (or keeps
the pages committed). Splitting a screen into several files does not shrink anything.

```
<docs>/prototype/screens/<id>.html     [Y] one source per screen: states + interactions   (you write these)
<docs>/prototype/screens/_shared/*.css, *.js   [Y] optional: CSS and scripts every screen uses (below)
<docs>/prototype/changes.md            [Y] optional: change ids for the main screens (below)
<docs>/prototype/screens.json          [G] screen → route, files, states, approval, status (build-prototype.py only)
<docs>/prototype/tours/<flow>.json     [Y] walkthrough scripts                              (tours.md)
<docs>/prototype/proposals/<name>/<variant>/screens/<id>.html   [Y] a variant's screen files (+ idea.md, _shared/)
<docs>/prototype/proposals/<name>/changes.md   [Y] the proposal's change ids (below)
<docs>/prototype/proposals/<name>/…/*.html   [G] both views per variant + index.html (build-prototype.py --proposal)
<docs>/prototype.html · app.html · screens.html   [G] rebuilt by build-prototype.py, never edited
<docs>/decisions.md                    [Y] the decision log; shown per screen in the prototype
```

## The screen file contract

One file per screen, `<docs>/prototype/screens/<id>.html`. `<id>` is the file name (letters, digits, `_`, `-`) and the
`data-screen` value. A file whose name starts with `_` or `.` is never a screen (keep drafts as `_draft.html`).

```html
<style>
[data-screen="booking"] form { display: grid; gap: var(--spacing-3); }
@container plumb-frame (min-width: 48rem) {
  [data-screen="booking"] form { grid-template-columns: 1fr 1fr; }
}
</style>
<section data-screen="booking" data-title="New booking" data-order="2">
  <h2>New booking</h2>                                <!-- shared: shown in every state -->
  <div data-state="ready"> … the form … </div>         <!-- the first state is the default -->
  <div data-state="loading"> … skeleton … </div>
  <div data-state="empty"> … </div>
  <div data-state="error"> <p role="alert">That table was just taken. Nothing was booked.</p> </div>
  <div data-state="success"> … </div>
</section>
<script data-screen-script>
var form = screen.querySelector(".booking-form");
form.addEventListener("submit", function (event) {
  event.preventDefault();
  plumb.setState(form.elements.guest.value.trim() ? "success" : "error");
});
</script>
```

- **One `<section data-screen>`** with `data-title` (the name in the navigation) and optional `data-order`.
- **States** are the outermost `data-state` blocks. Name them with plain words: `ready` (or `default`), `loading`,
  `empty`, `error`, `success`, `disabled`, `long-text`, `zero`, `offline`, … Every state `references/ux.md` asks of this
  screen (`### States per screen`) must exist; the audit suggests the missing ones.
- **Styles** go in `<style>` and every selector starts with `[data-screen="ID"]`, so screens never style each other.
  Responsive layout follows the frame the screen sits in (phone or desktop), not the window: use
  `@container plumb-frame (min-width: 48rem)`, never `@media (min-width: …)`.
- **Only tokens.** Colours, type, spacing, radius, shadow and motion come from the token block every page inlines
  (`var(--color-primary)`, `var(--spacing-4)`, `var(--text-sm)`…). No raw hex, no off-scale sizes: `audit.py` must exit 0
  on the prototype like on the code. The theme switches by itself; never write dark overrides.
- **Scripts** (`<script data-screen-script>`) are a function body run once per rendered copy of the screen as
  `function (screen, plumb) { … }`: `screen` is the section element; `plumb.setState(name)`, `plumb.go(id, state)`,
  `plumb.state()`, and `plumb.catalogue` (true inside `screens.html`). **Select inside `screen`, by class or data
  attribute (`screen.querySelector(".booking-form")`, `[data-test=save]`), never by id and never from `document`:** in
  `prototype.html` every screen shares one document, and in `screens.html` every copy is its own separate document, so
  ids and globals do not mean the same thing in both. Ids in markup are fine for labels and ARIA (`for`, `aria-labelledby`)
  as long as they are unique across the product.
- **Links between screens:** `<a href="#screen-home">` or `plumb.go("home")`; a state: `#screen-booking/error`. They
  work in both `prototype.html` and `app.html` (whose own addresses are `#/home` and `#/booking/error`).
- **App shell sidebar** (optional): mark a screen's sidebar `data-app-sidebar` and `app.html` keeps it in view while
  the page scrolls (`position: sticky; top: 0; height: 100dvh` from the md breakpoint). Nothing else about the
  screen's layout is assumed; below the breakpoint the screen's own CSS decides.
- **Fidelity hooks** (optional, they make the audit sharper): `data-component="BookingCard"` names the component an
  element is built from; headings, button text, labels and legends are compared with the code's copy.
- **Tour targets** must exist in this file's markup (they may be hidden in a state); see [tours.md](tours.md).
- **Guide text** (optional): `data-guide="Start a new booking here"` lists an element under "What you can do" in the
  prototype's Guide panel. A change id in front, `data-guide="F01 · what changed and why"`, shows as a chip (below).

## Shared files (`_shared/`)

CSS and scripts several screens use (an app shell's layout, a toast helper) live once in `<screens folder>/_shared/`:
the main `prototype/screens/_shared/` and each variant's `screens/_shared/`. Only `*.css` and `*.js` there are read,
in name order (prefix them `10-base.css`, `20-shell.css` to choose the order). No copy script: nothing else to run.

- **CSS** is inlined once per page, before the screens' own styles (a screen can override it). Scope it yourself:
  start each selector with `[data-screen]` (every screen) or `[data-screen="id"]`; any other selector is a warning,
  because it also styles the prototype's own panels. Tokens only, as in a screen file.
- **JS** files run for **each** screen (each copy in `screens.html`), before the screen's own script, as
  `function (screen, plumb) { … }` with the same API (`plumb.screen` says which screen). A shared script that throws is
  logged with its file name; the others still run.
- **Same contract as a screen file:** inlined as written, so `</script` in a JS file or `</style` in a CSS file, and
  anything that loads from the network or another file (`fetch(`, `new XMLHttpRequest`, `WebSocket`, `EventSource`,
  `sendBeacon(`, `import`, CSS `@import`, `url(https://…)` or `url(//…)`) exits 2 naming the file and line.
- **Approvals:** the shared files are part of every screen's approval. Editing one makes the approval of every screen in
  that folder stale, and the build's note names the shared file ("… changed since Ana approved it on 2026-10-14 (the
  shared file: docs/design/prototype/screens/_shared/base.css changed; shared files reach every screen)"). Show the
  change and ask again. A project with no shared files keeps the hashes it had: earlier approvals stand.

## Change ids

Mark each element a change touched with an id: `data-guide="F01 · Moved the list to the left: regulars scan it first"`.
An id is a letter and digits (`F01`, `P2`), then `·`; anything else is plain guide text and never checked.

- **Proposals:** list the ids in `<docs>/prototype/proposals/<name>/changes.md`, one line each:
  `- **F01** title: what changed and why` (other lines are free text). `build-prototype.py --proposal <name>` (and
  `--check`) exits 2 when a screen uses an id that is not listed, or there is no `changes.md`, naming the screen file and
  the id; it warns about a listed id no screen uses; the index lists the changes with where each is used.
- **Main prototype:** ids are checked the same way only when `<docs>/prototype/changes.md` exists.
- The Guide panel shows the id as a chip next to the text, so a reviewer can say "F01 is right, F02 is not".

## The app view (`app.html`)

`<docs>/app.html` shows the product as it will feel: every screen full window, with no prototype panels (no screens
list, state switcher, toggles, decisions or player). Use it to demo; use `prototype.html` to review.

- Addresses: `app.html#/<id>` and `app.html#/<id>/<state>` (`#screen-<id>[/<state>]` works too). It opens on the first
  screen by `data-order`; an unknown id opens that screen.
- Screen scripts run with the same `plumb` API (`plumb.catalogue` is false), and `window.plumbPrototype` /
  `window.plumbTheme` are there, so a screen's own theme toggle works. The theme follows the system until that toggle
  picks one; the choice is remembered in the browser when it allows it.
- The window is the frame, so `@container plumb-frame (min-width: 48rem)` rules follow the window width (the width
  inside a classic scrollbar: on Windows, a window just over 48rem may show the layout below md). A screen that is
  longer than the window scrolls the page; a change that opens a dialog (a state change, `plumb.go`, a link to that
  state) scrolls it into view, while a dialog that was already showing never moves the page; `data-app-sidebar` keeps
  a sidebar in view.
- Screens may use `position: fixed`: toasts and bars sit on the window, as in the product. (For Plumb's own pages:
  never give the frame or stage `transform`, `filter` or `contain`, which would pin them to the page.)
- Generated and offline like the other pages; each proposal variant has its own `app.html`.

## The quality bar (Effective HTML)

When the Effective HTML skills are installed, variants, screen files and directions follow `html-prototype` and
`design-artifact`. When they are not, these rules are the bar.

**The project's design system outranks Effective HTML.** In a project, the `<project>-design-system` skill (its
tokens file, `design.md` and `references/`) is the authority for every page and screen Plumb produces. Effective HTML
(`html`, `html-prototype`, `design-artifact`) is followed for **craft only**: real content, states, interactions,
accessibility and polish. It never chooses the palette, typography, spacing, radius or motion; where its guidance
conflicts with the project's system, the system wins. Prototypes and screen files use only the inlined token block
(CSS variables), and the audit exits 0 on them. The one exception is `/plumb:create`'s directions page, written before
any system exists: each direction is a candidate system, so there Effective HTML may shape the look too.

- **Real content:** the product's real words, names, numbers and lengths (a long name, a zero, a big number), never
  lorem ipsum or "Item 1".
- **Every state** the screen can be in, designed, not improvised: loading, empty, error, success, disabled, long text,
  zero, offline where relevant; every control state (default, hover, focus, pressed, disabled, loading).
- **Working interactions:** links, tabs, dialogs, menus, form validation and toasts work as they will in the product.
  In `prototype.html` the frame is the containing block for anything a screen fixes in place (a `position: fixed`
  scrim, dialog or toast sits inside the frame, as on a device of that width); a state change that opens a dialog
  (`dialog[open]`, `role="dialog"` / `"alertdialog"`, `aria-modal="true"`) scrolls it into view, and a dialog that was
  already on show never moves the page.
- **Keyboard and focus:** every control reachable by Tab in a sensible order, a visible focus ring (the focus token),
  Esc closes what opened, labels on every field and icon-only button.
- **Both themes:** check light and dark; nothing disappears or loses contrast in dark.
- **Reduced motion:** with `prefers-reduced-motion`, nothing slides; fades stay only when the tokens file's
  `$extensions.plumb.motion.reduced` is `"keep-fades"`, otherwise state changes are instant.
- **No generic look:** a deliberate hierarchy (one primary action per view), the system's type pairing and spacing
  rhythm, real density for the audience; nothing that looks machine-made or like three recolours of one layout.
- **Mobile platforms** sit in a phone frame with that platform's conventions (iOS navigation bar and tab bar, Android
  top app bar and navigation bar, 44 pt / 48 dp targets).
- **Offline:** nothing loaded from the network: no CDN, no hosted fonts, no remote images (system font stacks or the
  project's own font files).

## Variants (`/plumb:prototype`)

2–3 variants of the same screen or flow that differ in **UX** (layout, flow, density, navigation), all on the same design
system. Each variant comes as **both views**, so states are compared, not only the happy path:

```
<docs>/prototype/proposals/<name>/
  a-<slug>/screens/<id>.html   [Y] variant A's screen files, in the contract above (what goes to main if chosen)
  a-<slug>/idea.md             [Y] optional: "# Title", the idea in a sentence or two, "- " lines with the trade-offs
  a-<slug>/prototype.html      [G] variant A, clickable: its screens, navigation, interactions, state switcher,
                                   phone/desktop and light/dark toggles (the main prototype's shell)
  a-<slug>/app.html            [G] variant A, full window for a demo (the main app view)
  a-<slug>/screens.html        [G] variant A, catalogue: every screen × every state, light and dark side by side
  b-<slug>/…
  index.html                   [G] the variants side by side: title, idea, trade-offs, links ("Review: prototype.html ·
                                   Demo: app.html", and every state), light/dark
```

- You write only the screen files and `idea.md`; `build-prototype.py --proposal <name>` builds every page (generated,
  byte-stable, offline, the project's token block inlined, so token-true). `--check --proposal <name>` says when one is
  stale. Never edit the generated pages.
- When tokens change, `build-tokens.py` and the main `build-prototype.py` build refresh the token block of every
  generated proposal page, so old variants still render; their screen files are never touched. Proposals are the record
  and are not otherwise kept in step with code.
- A variant's pages sit in its own folder, so a relative image path in a variant's screen file resolves from that
  folder; check such paths when the screen is copied to `<docs>/prototype/screens/`.
- The chosen variant's screen files (and its `_shared/` files) are copied to `<docs>/prototype/screens/` (the main
  prototype); the others stay.

## Approvals and the map

- `build-prototype.py --approve <id>` records the user's yes to a screen (who, when, a hash of the screen file).
  **Never run `--approve` (or record an approval) without the user's explicit yes to that screen** in this
  conversation: show the screen (its `prototype.html#screen-<id>` link), ask "Approve <screen> as the reference to
  build?", wait for the answer. Never chain it after another command (`--synced x && --approve x`), never approve on
  the user's behalf because a flow "usually" ends approved. Editing the screen file afterwards makes the approval
  stale (`screen-unapproved`): show the change and ask again.
- `--map <id> --route=<route> --files <globs>` links a screen to its route and source files once they exist (or are
  agreed); the screen is `to-build` until every glob matches, then `built`. Pass the route as one argument
  (`--route=/`, `--route=/billing`): Copilot CLI reads a bare `/` as a path and asks for access to it.
- `--synced <id>`: the screen file was updated to match code that was already built (a small fix, code written before
  Plumb). Listed for the user to confirm later with `--approve` (their yes, asked); it never blocks.
- **Prototype first.** A new screen or route is created in the prototype, approved, then built; the edit check refuses a
  new page file with no approved screen (`fix: /plumb:prototype <name>`). Changing what an existing screen shows or how
  it behaves starts with its screen file and the user's approval. Small fixes that change neither (logic bugs, typos,
  data wiring) need no prototype step.

## Always in step, both ways

- **prototype → code:** a screen marked `to-build` stays in `/plumb:status` and the audit until its route exists.
- **code → prototype:** when a screen's source files change and its screen file does not, the end-of-turn check stops
  the agent once ("update prototype screen booking: states loading, empty"), and the audit reports `screen-drift` as an
  error. Update the screen file to show the change, ask, then `--approve` (or `--synced` for a small already-built fix).
- **a route with no screen** is `route-not-prototyped`.
- A UI change is not done until the main prototype shows it.

## Decisions on screens

Each entry in `<docs>/decisions.md` (`## DS-YYYYMMDD-slug · title`, see `templates/decision-entry.md`) with a
`- Screens: booking, home` line (or `all`) shows in that screen's "Why it looks like this" panel and on the Decisions
page. Entries are append-only; the id is collision-free so branches can add decisions without conflicts. Mirror each
entry into `docs/decisions.md` when the project keeps one, and add a line to `design.md`'s revision notes.
