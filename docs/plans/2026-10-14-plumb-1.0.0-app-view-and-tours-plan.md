# Plumb 1.0.0: app view, tours and field fixes (owner amendment, 2026-10-14)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Each task runs in its
> own worktree branched from `feat/1.0.0`, is reviewed, then merged one at a time with the full suite (3.13 and 3.9,
> Playwright included) after each merge.

**Goal:** add a full-window app view of the prototype, tours that play in it, a walkthrough player that never hides
behind the screen and can get out of the way, tour checks, and fixes for nine Plumb mistakes found in field use
(inventory, overrides, contrast fixes, scaffold defaults, catalogue size, the Bash guard). Everything below is the
complete requirement: this plan stands on its own.

**Spec:** `docs/specs/2026-10-11-plumb-design.md`; this plan adds §3.4.2 (app view) and changes §3.4.1 (tours) and
§6.3 (`build-prototype.py`) in Task 1 and Task 3. Still 1.0.0 (unreleased): CHANGELOG and `upgrades/1.0.0.md` entries go
under 1.0.0.

## Global constraints (unchanged)

- Python 3.9+, standard library only; UTF-8 and `\n` everywhere; no `shell=True`; works on Windows, macOS, Linux.
- **No downloads, ever.** Nothing installs or downloads anything (no pip, npm, browsers, fonts). The runtime tour check
  uses only a browser already on the machine (screenshot.py's search); none found → a `note:` line, the static checks
  still run, and the skill asks the user and waits. `PLUMB.md`, every skill and the AGENTS row keep saying so (Task 11
  adds a test that pins it).
- Generated pages: byte-for-byte deterministic, `GENERATED … do not edit` header, nothing from the network, light and
  dark, `--check` covers every one.
- Every refusal `error:` + `fix:` / `ask the user:`, with a test. Scripts give evidence, not answers.
- No AI attribution in commits (tell every subagent).
- **Generic (owner, 2026-10-14).** Every fix works for any project, stack and layout: monorepo or not, any UI
  package path, any token names Plumb's format allows, any screen markup. No assumed class names, folder names or
  values; tests use neutral fixtures plus at least one variation (another folder name, another stack shape) so a fix
  is not shaped to one repo. Where a project detail is needed, it comes from the recorded settings (`PLUMB.md`) or a
  documented hook (`data-app-sidebar`), never a guess.

## Design (what the owner asked for, and the rulings)

**A. App view.** `build-prototype.py` also writes `<docs>/app.html`: every screen full window, no prototype panels.
Hash routes `#/ID` and `#/ID/STATE` (also accepts `#screen-ID[/STATE]`, so prototype links keep working). The same
screen-script API as `prototype.html`: `function (screen, plumb)` with `plumb.setState`, `plumb.go`, `plumb.state`,
`plumb.catalogue === false`, plus `window.plumbTheme` and `window.plumbPrototype` (`go`, `setState`, `current`, `screen`,
`setTheme`, `on`). Theme: the system setting until the screen's toggle picks one, then remembered in `localStorage`
(try/catch, per-viewer convenience). The window is the frame: `container: plumb-frame / inline-size`, so the md
breakpoint follows the window. A same-screen state change scrolls an opened dialog into view.
- *Ruling A1:* "the sidebar sticky" is generic through a documented hook: an element with `data-app-sidebar` in a
  screen is `position: sticky; top: 0; height: 100dvh` at the md breakpoint in app.html (nothing else about the
  screen's layout is assumed). Costs little if wrong: one attribute.
- *Ruling A2:* app.html opens on the first screen by `data-order` (no project-specific forwarding).
- Proposals: `proposals/<name>/<variant>/app.html` for every variant, linked from the proposal index next to
  `prototype.html`. `/plumb:prototype` and `reference/prototypes.md` name both links: **prototype.html to review,
  app.html to demo.**

**B. Tours.**
1. Each tour file gets `"view": "app" | "prototype"`. **Missing means `app`** (the owner: default app).
   `/plumb:tour` asks **"Where should it play?"** right after the audience question: *Full-window app (Recommended)* ·
   *Prototype page (with the screens list and the decisions rail, for a design review)*. `tours/<id>.html` follows it:
   `app` = the app view with the player on top; `prototype` = today's page. `prototype.html#tour-<id>` keeps playing
   every tour in the prototype. app.html itself carries no player (a clean demo).
2. Player (`player.js`, `player.css`, `prototype-shell.html.tmpl`, the new app shell):
   - `.pp-frame` (and the app frame) get `isolation: isolate`: screen z-indexes can never cover the dock, subtitle,
     cursor or labels;
   - `find()` skips nodes whose computed `visibility` is hidden (or inside such a node) and nodes outside the stage;
   - title cards are pinned to the viewport (`position: fixed`) on long pages;
   - a tall target (taller than the space above the dock) scrolls to `block: "start"` when the step has labels, else
     `"nearest"`;
   - **Hide panel**: a button in `.pl-dock-top` and the `H` key (not while typing). The dock hides; play keeps
     narrating in the subtitle; a small pill brings it back (the step title in guide mode, only the button in play
     mode). Kept in `localStorage` (try/catch). On every page that has the player;
   - the player chrome takes the project's tokens where they exist: `--pl-accent: var(--color-primary, <today's>)`,
     surface, outline, on-surface, fonts, radius, shadow; today's values stay the fallbacks.
3. On a prototype-view tour page (and in prototype.html while a tour runs) the screens list and the
   decisions/Guide rail collapse while a tour runs, so the frame keeps at least the screens' 48rem breakpoint; they
   come back when the tour ends.
4. Tour checks:
   - `build-prototype.py --check-tour FILE`: validates one tour file against the screens, writes nothing, exit 0 / 2.
   - It also **warns** when a step's target sits inside an element the screen's own CSS hides below a container
     breakpoint (`display: none`, `visibility: hidden` or an off-canvas `transform` outside an
     `@container plumb-frame (min-width: …)` rule that shows it again): "visible only when the frame is ≥ 48rem".
   - *Ruling B4:* the runtime pass is plugin-side, `scripts/check-tour.py <docs>/tours/<id>.html` (not copied into
     projects, like screenshot.py): it finds a browser with screenshot.py's search, writes a scratch copy under
     `<project>/.plumb-tmp/` with a checker script, runs it headless with `--dump-dom` at 1280 and 1440 wide, in guide
     and play mode, and reads the results. Per step: the right screen and state, the target and labels visible and in
     the viewport, the dock not covered (`elementFromPoint`). Problems: exit 2, one line per step (`step 12 (Users ›
     Invite): the target is hidden (visibility: hidden) at 1280`). No browser: exit 3 with the screenshot.py note.

**C. Field fixes (one fix, one failing test first, one false-positive test each).**
- **`audit.py --inventory`, radius.** Today Tailwind radius classes are read with Tailwind's defaults
  (`rounded-lg` = 8px). A project whose CSS sets `--radius: 0.625rem` and, in `@theme` / `@theme inline`,
  `--radius-sm: calc(var(--radius) - 4px)` … `--radius-xl: calc(var(--radius) + 4px)` (the stock shadcn setup) renders
  `rounded-lg` as 10px. Fix: resolve each `rounded-*` class against the project's own `--radius-*` variables (plain
  lengths, `var(--radius)`, `calc(var(--radius) ± N px|rem)`), falling back to Tailwind's defaults only for sizes the
  project doesn't define. False positive: no `@theme` radius → today's numbers.
- **`audit.py --inventory`, colour clusters.** CIEDE2000 < 3 clustering merged a named CSS variable's value (a theme or
  chart series colour such as `--chart-3`) with palette-class values used in components (`bg-emerald-500`). Fix:
  cluster only within one source kind; a value defined as a named theme/chart variable is never merged with palette
  classes; the output says which kind each cluster is.
- **`build-tokens.py --overrides`, sidebar roles.** For shadcn `--sidebar-<x>` names the plan picked the generic role
  (`--sidebar-accent` → `{color.sunk}`) although the tokens file has a sidebar-specific role. Fix: for `sidebar-<x>`
  (and `sidebar-<x>-foreground`), prefer an existing `color.sidebar-<role>` / `color.on-sidebar-<role>` token, where
  `<role>` is `<x>` or its known synonym (`accent` ↔ `active`), before the generic mapping. False positive: no sidebar
  token → today's generic mapping.
- **Contrast fix for `on-X` on `X`.** When `on-X` is white or black (text on a filled control) and the pair fails, the
  fix today only steps `on-X` (white → black: a big look change). Fix: also compute the nearest `X` (same hue, stepped
  lighter or darker) that passes with `on-X` unchanged; list that option first, then the `on-X` option; show both with
  their computed ratios, per theme. Shown by `build-tokens.py --contrast` and the audit's `contrast` fix text.
- **next/font variable on `<body>`.** When an override prepends a next/font variable (`var(--font-…)`) into
  `@theme static` on `:root`, but the app applies the font's `.variable` class on `<body>` (the stock create-next-app
  layout), the variable is undefined at `:root` and the whole font stack is invalid. Fix: `--overrides` reads the root
  layout from the recorded `Routes:` (`next-app` kind: `<route root>/layout.(tsx|jsx|js|ts)`), and if a `.variable` used
  by a prepended font is applied on `<body>` and not `<html>`, adds a `by_hand` item: "move `<name>.variable` to the
  `<html>` className in <file>:<line>". No `Routes:` / not next-app → no check, no noise.
- **`scaffold.py`, `Allowed raw values` default.** Today it defaults to `components/ui/**` from the repo root, which
  matches nothing when the UI package sits in a subfolder (`<ui package>/src/components/ui/`). Fix: derive it from the
  recorded UI package path and `components.json`'s `aliases.ui` (resolved through the package's tsconfig `paths` /
  `@/` → `src/` when present), e.g. `web/src/components/ui/**`; and `--verify` reports (`warning:` + `fix:`) an allow
  pattern that matches 0 files. Test with two different package folder names.
- **`build-prototype.py`, catalogue size.** screens.html today holds one `<template>` per screen × state × theme, each
  a full render of the screen, so a large prototype gives a catalogue of tens of MB. Fix: one `<template>` per screen
  (all its states), shared by its light and dark copies and every state; the page picks the state when it builds each
  iframe; tokens once. Any generated page over 10 MB prints `warning: <file> is <N> MB …` with what to do (move inline
  images, SVG and data: URIs into files beside the screens, or git-ignore the page; with one copy per screen,
  splitting screens no longer shrinks a page — review ruling, 2026-10-14). Yardstick: a synthetic 20+ screen × 10 state fixture must grow with screens, not
  screens × states × 2.
- **`hooks/pre_edit.py`, Bash guard false positives.** Today a Bash command is refused when its text merely mentions a
  Plumb-owned or generated path: a heredoc writing a Makefile whose lines run the design system's scripts, a command
  that only reads `screens.json` with `json.load`, a Python check that imports a Plumb script, words like `append`,
  `.dump` or a `>` inside quoted code. Fix: refuse only real write targets on those paths: a redirect target (`>`,
  `>>`, `1>`, `&>`), `tee [-a]`, `sed -i` / `perl -i`, the destination of `cp` / `mv` / `install` / `rsync`, `rm`,
  `truncate`, `dd of=`, `ln` target, and in an inline script (`python -c`, a heredoc fed to an interpreter) a literal
  `open("<path>", "w"|"a"|"x"…)` or `Path("<path>").write_text/write_bytes`. Heredoc bodies written to another file and
  quoted strings are data, not targets. Reading, running and importing are allowed. Every write form above stays
  refused (tests for each).

**D. Change ids and shared files (owner: yes, 2026-10-14).**
- *Change ids:* a proposal (or any screen change) may mark each changed element `data-guide="<ID> · what changed and
  why"`, where `<ID>` is a letter and digits (`F01`, `P01`). The ids are listed in the proposal's `changes.md`
  (`<docs>/prototype/proposals/<name>/changes.md`, one `- **F01** title: what and why` line each). `build-prototype.py
  --proposal` checks every id used exists in `changes.md` (exit 2 with the screen, the id and the fix) and warns about
  listed ids no screen uses. The Guide panel shows the id as a chip; the proposal index lists the changes.
- *Shared files:* `<screens folder>/_shared/*.css` and `*.js` (the main `prototype/screens/` and each variant's
  `screens/`). CSS is inlined **once** per page (sorted by name), selectors scoped by the author; JS files run for
  **each** screen before its own script, as `function (screen, plumb)`, in name order. They feed the screen hash
  (editing a shared file makes the approvals of every screen it reaches stale, said in the build output), the catalogue,
  app.html and the tour pages. Same contract checks as screen files (no `</script>` inside, no network). No copy script.
- Tests: an unknown id refuses; an unused id warns; shared CSS appears once; shared JS runs per screen before the
  screen's script with the same API; approval staleness after a shared-file edit; deterministic.
