What a project gets from Plumb

A plumb line keeps a wall true while it goes up. Plumb does that for a product's design: one design system the agent must build with, a prototype of every screen that you approve first, and checks that stop drift while Claude or Copilot builds. You stay in charge: one question at a time, nothing written without your OK, nothing installed or downloaded.

The flow

From an idea to a built screen

Every step is a command you run, in Claude Code or Copilot CLI. The brass steps wait for you: nothing is built until you have picked and approved it. UI work is always prototype first: the screen is approved, then built to match.

Set up/plumb:init

Finds the project, asks new or existing.

Designcreate · extract

Interview, directions, the design system. You choose.

Prototype/plumb:prototype

2–3 variants of a screen. You approve one.

Build

The agent builds to the approved screen. Hooks hold every edit true.

Checkaudit · ux

Consistency, UX and prototype fidelity reports.

Keep trueupdate · upgrade

Change the design; take new Plumb versions.

Commands

Eleven commands, one job each

The same commands work in Claude Code and GitHub Copilot CLI (in Kiro, a preview pending its live check, they are /plumb-init, /plumb-create, …). The complete guide, with an example session for each, is docs/USAGE.md.

CommandUse it whenWhat it does
/plumb:initFirst time in a projectFinds the right place (monorepo, separate frontend, parent folder, linked repos), shows what it found and waits for your OK, asks new or existing, and runs create or extract. Adds the rules to AGENTS.md / CLAUDE.md.
/plumb:createA new projectAsks about the product, then each design decision. Shows 2–3 directions, writes the design system, then prototypes the key screens.
/plumb:extractA project with UI alreadyLists every colour, size and component in use, merges near-duplicates, builds the same design system and a prototype of every existing screen.
/plumb:prototypeA new screen, tab, flow or interaction2–3 variants, each clickable and with every state. You approve one; it joins the main prototype with a default walkthrough. Building comes after.
/plumb:tourA demo, a training, an onboardingWrites a custom walkthrough: captions, callouts, labels, pointing styles, chapters, “your turn” steps. Also a standalone HTML file to share.
/plumb:auditAny timeChecks consistency, contrast, drift and that the built UI matches its prototype, then an agent review. HTML report; offers Slate tickets. fix repairs with your OK; improve makes the screens and the system better.
/plumb:uxAfter building a screenReviews the experience: states, forms, keyboard path, wording, visual polish, side by side with the prototype.
/plumb:updateThe design changesChanges tokens or components, adds a platform, regenerates everything, records the decision.
/plumb:upgradePlumb has a new versionShows what's new, updates the copied scripts, migrates without deleting your values, asks before each step.
/plumb:statusYou want a health checkRead-only: version, platforms, placement, stale files, audit counts, screens to build and to approve, checks on or off, the next step.
/plumb:feedbackPlumb itself got something wrongPlumb mistakes only: the agent records each script, hook or skill result it had to correct in ~/.plumb/feedback/, outside the project. Typed, it reports them grouped, most frequent first, and drafts issue text that is never sent. Your project's design issues stay with /plumb:audit.

/plumb:create

The interview

One question at a time, each with options and a recommendation that follows from what you said about the product. Existing projects run /plumb:extract instead: the values come from the code, and the interview only asks what the code can't answer.

A
The product first

What you are building, who it's for, where and how often it's used, the key tasks, the feel you want, and any brand you already have.

Who will use this most?● People who keep it open all day (Recommended from your brief)○ Occasional visitors on their phones○ Both, equally
B
Platforms and stack

Web, iOS, Android. The framework and styling (Tailwind v4, v3, plain CSS) are detected, then confirmed.

C
Design decisions

Personality, density, accent, neutrals, semantic colours, label colours, type, spacing, radius, elevation, motion, icons, dark mode, accessibility target, vocabulary and voice, and UX patterns: navigation, page anatomy, forms, states, feedback, onboarding.

D
Directions

Two or three distinct, finished-looking directions on one page, each with a real screen of your product in light and dark. You pick one or combine them.

E
Generate

Tokens, then every theme, then contrast computed and fixed with your OK, then the skill files, then components written in your framework, then the audit must pass, then the specimen page.

F
Prototype the key screens

The first main prototype, from the key tasks in A, with walkthroughs if you want them.

G
Record every decision

Each choice goes in docs/design/decisions.md: the options, the one chosen, why, and who decided.

# <Project> design system

<one paragraph: what the product is, who uses it, the feel>

## Workflow
1. Prototype first. Update or create the screen with /plumb:prototype, show the
   user, get their approval, then build it to match.
2. Inventory before building (references/inventory.md). Reuse or add a named variant.
3. Spec first (references/components.md), then only the platform file.
4. Name every visual decision with a token. A missing value goes into the tokens file.
5. Build every state from the prototype and references/ux.md, light and dark.
6. Check: the accessibility checklist, make tokens-check, make design-audit.
7. Report what you reused, what you created and why.

## Hard rules
- One token source. Generated files are never edited by hand.
- Closed scales. No raw colours or arbitrary sizes; layout geometry is the exception.
- <rules from your decisions: type scale, motion, focus, status words…>

docs/design/prototype.html

One prototype of the whole product

Every screen, clickable, working the way the real UI works. Each screen has its states, a phone and desktop view, light and dark, the decisions behind it, and a guide. It is built from one source file per screen, kept in step with your frontend, and checked by the audit.

/plumb:prototype makes the screens. The walkthrough player is part of every prototype; /plumb:tour only writes the script it plays (which steps, which words), for a review or a client demo.

Walkthroughs

Tours: demos, training and onboarding

Every prototype can play a walkthrough. /plumb:prototype writes a default one for each flow it builds; /plumb:tour writes custom ones for a client demo, a training session or a new teammate. Each tour is also its own HTML file in docs/design/tours/, so you can send it to someone and it opens straight into the tour, offline.

Adding textCaptions like subtitles, callouts on a chosen side, labels on several elements at once, notes anywhere, title cards between chapters, text typed into real fields.
PointingSpotlight, ring, arrow with a label, beacon, zoom, and a cursor that clicks in play mode. Several targets in one step.
Teaching“Your turn” steps wait for the learner to click the real control; a wrong click gets a hint. In play mode the same step runs by itself.
PacingChapters, intro and closing cards, a default speed per tour, longer holds on important steps, links to any scene.

/plumb:audit

An audit report

An HTML report in docs/design/, a terminal summary and an exit code (0 means no errors). Every issue says where it is, what is wrong and the exact fix, naming the token to use. It also checks contrast in light and dark, generated files that drifted, and that the built UI still matches its prototype. After the rules, the agent reviews what no rule can express (marked agent review), and an Improvements section ranks suggestions that never fail the audit. With Slate set up, it offers to turn the fixes into tickets.

Hooks, in Claude Code and Copilot CLI

While an agent builds

One session, start to finish. Init asks whether to turn the checks on (recommended), and each can be switched off in PLUMB.md. The hooks run only the plugin's own scripts, never the copies in your project, and never block your work when something is missing.

Session starts 
Plumb: <project>-design-system 1.0.0 · tokens up to date · 0 audit issues · read the skill before UI changes
Plumb mistakes (a Plumb script, hook or skill got it wrong) → /plumb:feedback
A new page with no approved prototype 
error: app/reports/page.tsx is a new screen with no approved prototype
fix: /plumb:prototype reports (design the screen, get the user's approval, then build it to match)
You approve a variant; it is written into the main prototype

The decision is recorded with who chose it and why. Now the page can be created.

An edit bypasses the tokens, or touches a generated file 
error: app/globals.css is generated from the design tokens; a hand edit is lost on the next build
fix: change the tokens with /plumb:update, then rebuild: python3 …/scripts/build-tokens.py

Refused before it lands, with the token or command to use. Only errors the edit adds count, so older code never blocks.

The agent finishes its turn 
Plumb end-of-turn check: 1 new design-system error in the files changed this session.
Fix them now, or tell the user why not (this check stops you once):
error: app/reports/page.tsx line 12: raw colour #b42318

The agent is stopped once, fixes it, and finishes. It cannot loop. A built screen that changed without its prototype stops it the same way.

When Plumb itself gets something wrong (a script's guess the agent corrects, a hook that crashes and fails open), the agent or the hook records that Plumb mistake in ~/.plumb/feedback/ on your machine, outside the project; /plumb:feedback reports them for Plumb's developers.

When Plumb has a new version

The session line tells you when the plugin is newer than the project. Upgrade never runs by itself, never deletes your values, and asks before every step that changes your files.

For enterprises

What it needs, and what it never does

NeedsPython 3.9 or newer with its standard library, and Claude Code or Copilot CLI (Kiro: a preview, live check pending). git is optional. macOS, Linux and Windows, over SSH and in tmux.
NeverNo npm, pip or other installs. Nothing downloaded while it runs. Every generated page opens offline: no CDN, no hosted fonts.
Asks, then waitsThe rule Plumb adds to AGENTS.md / CLAUDE.md: don't install or download anything; if something is missing, ask the user and wait for their decision.
Optional extrasEffective HTML skills, a browser for screenshots, make, Slate. Each has a fallback, so none is required.

The complete guide is docs/USAGE.md; the full design is docs/specs/2026-10-11-plumb-design.md. Plumb works in Claude Code and GitHub Copilot CLI, on macOS, Linux and Windows. This page loads nothing from the network.
